# Semantic Review - Redemption Code System (v1)

**Verdict**: NEEDS_CHANGES

## Issues Found

### 1. TYPE_REDEEM constant unused (Medium)
`TokenTransaction::TYPE_REDEEM` was added but `RedemptionCodeService::redeem` calls `TokenService::credit` which writes `TYPE_CREDIT`. Either use a new `redeem()` method on TokenService that uses `TYPE_REDEEM`, or remove the dead constant.

### 2. No rate limit on /redeem-code (High)
The endpoint accepts any authenticated user's POST with no throttle. Add `throttle:5,1` (or similar) to prevent brute-force code enumeration. The AI editor route already has `throttle:10,1`.

### 3. Bulk code generation is not atomic (Medium)
`generateCodes` creates codes in a loop with individual `create()` calls and no wrapping transaction. If the process dies mid-loop, partial codes exist. Wrap in `DB::transaction`.

### 4. Unbounded retry in generateUniqueCode (Low)
The `do/while` loop retries until it finds a unique code but has no iteration cap. Add a max-attempts guard (e.g., 10 tries then throw).

### 5. Route model binding ambiguity for `{code}` (Low)
The route parameter `{code}` in `/codes/{code}` resolves by primary key (id) by default. Consider renaming to `{redemptionCode}` to match model type hint.

### 6. cascadeOnDelete on created_by FK (High)
If an admin user is deleted, all codes they created (including used ones) are cascade-deleted, destroying redemption history. Use `nullOnDelete()` instead.

### 7. TierService failure can refund a successful render (Critical)
The tier update runs inside the job's try block after render completes. If `updateUserTier` throws, the catch block marks render as failed and refunds tokens even though the render output already exists. Wrap tier update in its own try/catch.
